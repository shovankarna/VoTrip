# Contributing

VoTrip is currently a solo-built project (see `docs/01-PRD.md`), so this doc
is intentionally lighter than a team-scale process — but it's written so it
still holds up the day a second contributor (human or agent) joins, without
a rewrite.

## Repository

Single repo, two independently-built applications:

```
VoTrip/
├── docs/
├── backend/     → Spring Boot (Maven)
└── frontend/    → Turborepo (pnpm): Next.js web + Expo mobile
```

A feature that touches both sides (e.g. a new endpoint plus the screen that
calls it) is normally **one PR** here, not two — that's the main advantage
of the single-repo layout. Keep the diff organized by folder even within
one PR so backend and frontend changes are easy to review separately.

## CI

GitHub Actions, path-scoped so a backend-only change doesn't trigger a
frontend build and vice versa (see `docs/03-TechStack.md` §10 for why
GitHub Actions was chosen — free tier at this project's scale).

**Triggered by changes under `backend/`:**
- `./mvnw verify` — unit tests + integration tests against a throwaway
  Postgres instance (matches the self-hosted-Postgres setup in
  `docs/03-TechStack.md` §8, not a mocked DB — ordering/position and
  cascade-delete behavior are genuinely DB-constraint-dependent and worth
  testing against the real thing)

**Triggered by changes under `frontend/`:**
- `pnpm lint` (zero warnings)
- `pnpm type-check`
- `pnpm build`

**Triggered by changes under `docs/` alone:** no build required — just a
lightweight check that internal doc references still exist (skip or keep
minimal for now).

Example path filter:

```yaml
on:
  pull_request:
    paths:
      - 'backend/**'
```

Both relevant workflows must be green before merge. There is no bypass
label for MVP — this is a low-traffic CI setup, not a suite slow enough to
need one. If that changes as the project grows, add a documented,
lead-approved bypass mechanism here rather than merging around red CI
silently.

## What needs a test, not just a green build

Given the domain (`docs/02-SRS-ERD.md`), these paths get actual test
coverage, not just "it compiles":

- Itinerary reordering — position collision → retry path, not just the
  happy path. A test that only reorders into empty gaps won't catch the
  bug that matters.
- Position rebalancing trigger (gap-too-small case).
- Expense split math — sums that must reconcile exactly (`DECIMAL(10,2)`,
  never float comparisons with an epsilon fudge).
- Settle-up / debt-simplification output for a few known input sets — this
  algorithm is easy to get "mostly right" in a way that's wrong for edge
  cases (e.g. everyone owes everyone the same amount).
- Cascade-delete behavior — deleting an itinerary item or travel leg must
  leave the linked `EXPENSE` row intact with the FK nulled, not deleted.
  This is the kind of thing that's invisible until it silently loses money
  data in production.
- Authorization — a Member cannot edit itinerary/invite/remove members
  regardless of what the client sends; a user who isn't a `TRIP_MEMBER` on
  a trip cannot read or write its data, even if they're a Guide on a
  *different* trip.
- If `frontend/packages/domain-logic`'s settle-up implementation and the
  backend's `SETTLEMENT` recomputation ever disagree on the same input,
  that's a bug worth a regression test, not just a bugfix — the two are
  supposed to be kept in sync by hand (see `CLAUDE.md`), so a divergence
  will recur if untested.

## Branching & Commits

- Branch names: short, descriptive, prefixed by type and (optionally)
  scoped by folder when a change is single-sided —
  `feat/backend-itinerary-position-rebalance`,
  `feat/frontend-drag-drop-web`, `fix/expense-split-rounding` (no prefix
  needed when a branch is genuinely full-stack). If/when an issue tracker
  is adopted, switch to `feat/VT-123-short-description` and note the
  change here.
- Commits: [Conventional Commits](https://www.conventionalcommits.org/),
  scoped by folder where it helps —
  `feat(backend/itinerary): add position collision retry`,
  `fix(frontend/expense): correct split rounding on odd totals`.
- PR description should note which side(s) it touches (`backend`,
  `frontend`, or both) so CI expectations and review focus are clear at a
  glance.

## Database Migrations (`backend/`)

- Migrations are generated by the migration tool in use (Flyway/Liquibase —
  whichever gets adopted; keep this section updated once decided), not
  hand-written diffs against production.
- Any migration touching a constraint listed in `docs/02-SRS-ERD.md` (the
  uniqueness rules, XOR check on `DAY`, cascade rules on `EXPENSE`) should
  link back to that section in the PR description, so a reviewer can check
  the migration actually preserves the documented rule rather than quietly
  loosening it.
- Never hand-edit a migration that's already been applied anywhere outside
  your own local DB — write a new one.
- If a migration changes a shape that `frontend/packages/shared-types`
  depends on, update that package in the **same PR** — this is exactly the
  kind of drift the single-repo layout exists to prevent; don't let it
  happen anyway by landing them separately.

## Local Development Setup

```bash
# backend
cd backend
docker compose up -d postgres
./mvnw spring-boot:run

# frontend
cd frontend
pnpm install
pnpm dev
```

Requires Docker (for local Postgres) and a Firebase project (dev/staging)
with a couple of test accounts — there's no local auth bypass, since so
much authorization logic sits downstream of a verified Firebase token.
